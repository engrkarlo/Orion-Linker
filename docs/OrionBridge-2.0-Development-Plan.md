# OrionBridge 2.0 — Development specification

Status: proposed implementation contract; not a claim of completed features. Target: Paper 26.3, Java 25, OrionBot (Discord Components V2), Java inventory/dialog and native Bedrock forms. Repository: existing Orion-Linker repository, repurposed for OrionBridge. Preserve repository history and existing OrionBot compatibility until migration is verified.

Implementation update (alpha.7 development branch): Native OrionBot integration, reconnect-safe challenges, persistent containment, scoped task approvals, optional lobby, offline rank provider checks and multi-round appeal review are implemented in source. See [documentation index](README.md) and [acceptance](acceptance.md) for exact coverage, unsupported paths and required tests. This document remains the target specification.

## Goals and boundaries
- Mandatory one-to-one Minecraft/Discord verification after administrator setup; Java online identities and authenticated Floodgate XUIDs; offline Java only after supported authentication succeeds. No passwords or Microsoft credentials collected.
- Per-guild identity uniqueness; per-server verification, roles, channels, operation budgets, security policy; server or guild-wide moderation scope. No cross-guild data access or shared IP matching keys.
- Pull-first: only Minecraft Pterodactyl has HTTPS reverse proxy. OrionBot initiates all requests, including action POSTs. No bot-side listener required. Preserve existing v1 telemetry and Push compatibility; verify proxy methods, paths, body limits and timeouts. Short polling baseline, bounded long polling optional.
- No unrestricted remote console, arbitrary permission grants, silent IP-based bans, unbounded bulk work, or claim of complete protection from hostile plugins/host administrators.

## 1. Repository migration and compatibility
Copy current OrionBridge Java source, Maven build, tests, resources, README, workflow and bot transport into new repository with attribution/provenance. Keep OrionBot's production copy and v1 consumer working until a tested integration is deployed. Standalone bot adapter should have an explicit host interface; do not assume relative imports from OrionBot exist in the new repo. Use staged reviewable commits; no destructive history rewrite. Update OrionBot consumer separately via a versioned integration after contract tests. Target release 2.0.0 only after acceptance; intermediate prerelease versions honest about coverage.

## 2. Transport, persistence and isolation
Keep GET /v1/snapshot. Versioned v2 capabilities, health, event fetch, acknowledgement, typed actions and bounded queries. Server-scoped credentials with guild/server binding, TLS validation, existing SSRF-safe destination pinning, no redirects, separate read/control scopes, signature over method/path/body/timestamp/nonce, bounded replay cache, key rotation and credential-safe logs. Validate sizes/schema before dispatch; idempotent action IDs and durable receipts, expiry, monotonic policy versions, no stale authorization. Bot authoritative central SQLite state; plugin local durable cache/journal, transactionally persisted event IDs and action receipts. Prioritize security records over ephemeral chat; alert on queue/storage failure. Short poll 1–3s configurable with backoff, one outstanding per server and global concurrency limits. Never block main thread on network or database. Native game calls on correct scheduler; asynchronous FAWE hooks need thread-safe budget reservation. Durable delivery at least once with deduplication. Bot-side guild/server checks on every read/write, not just UI selection. Retention, backup and restoration tests; encrypted credential keys, least privilege. No inbound bot port in Pull mode.

## 3. Installation and mandatory verification
New install defaults to required verification but setup-required until pairing, channel, identity provider, permissions and console recovery confirmed. Existing installation retains all tokens/config, status panels and telemetry; enforcement explicitly activated after wizard validation. On login, authenticated identity check, local authorization lease, restricted state before gameplay. Deny movement, combat, build, inventory/container actions, drops/pickups, teleport and ordinary commands, chat; only exact approved verification/auth commands and disconnect. Closing menu never unlocks. Optional isolated lobby with safe original location/inventory handling; no permanent player state corruption. Disconnect/reconnect/respawn/world change and plugin lifecycle must not bypass. Fail closed for new players and sensitive actions during outage; bounded grace for verified players, no indefinite stale staff grants. Console-only break-glass recovery, no blanket OP bypass.

## 4. Identity and linking
Stable Java UUID, authenticated Bedrock XUID, explicit trusted proxy/Floodgate canonical identity resolution; no spoofed usernames. AuthMe-compatible post-auth linking for offline Java, fail closed if authentication unverified. One-to-one uniqueness on (guild, canonical Minecraft identity) and (guild, Discord ID), atomic simultaneous link transactions. Code cryptographically random, hashed/keyed at rest, short lifetime (5m), rate limited, bound to identity/guild/server/session, regenerate invalidates previous, single use. Discord modal claim plus Minecraft confirmation of displayed Discord identity, membership verification and expiry; no public codes. Staff-controlled transfers/recovery, optional minimum account age/membership, cooldown 7d configurable, recheck authorization on unlink/relink; retain historical association at incident time. Discord leave and role removal invalidate authorization promptly.

## 5. Interfaces and channels
Java default native dialogs, optional inventory, Bedrock native Cumulus forms with safe fallback to chat. Separate theme YAMLs: every text, color, material, layout, icon configurable; white dialog buttons by default, purple/pink branding optional. Native client limitations respected. Inventory click/session guards; no stale button actions; pagination, online heads and offline search; no synchronous skin requests. Player /ob dashboard: link, account, ranks, punishments, reports, appeals, help. Admin /ob admin: players, links, roles, moderation, security, correlation, staff access, lockdown, audit, settings, performance. Discord public persistent verification panel: Link Account modal, My Account, Help; private responses. Existing /mcserver manage > server > OrionBridge: Overview, Verification, Accounts, Roles, Punishments, Security, Evidence, Correlation, Trusted Operations, Channels, Audit, Settings. Components V2, minimal separators, compact code-block technical evidence, selectors, modal editing, pagination, confirmation and permission revalidation. Transient errors/confirmations disappear after 10s when feasible; incidents remain persistent. Channel Manager maps channel IDs per server/guild, optional creation/test with explicit permissions: verify, public chat, private staff chat, activity, security severity routes, punishment, account, role sync, audit, staff activity, health. No fixed channel names. Private channels checked for exposure; no public sensitive IDs/evidence.

## 6. Chat and role synchronization
Optional bidirectional chat, rank/role prefixes, skins, safe literal messages, configurable formats, no mention injection, no bot/webhook loops, rate limits and mute enforcement, linked members by default, separate authorized staff chat. Join/leave/death/advancement events configurable, respect vanish/listing privacy. Staff chat never routed public. LuckPerms mappings per server, explicit source/direction and conflict policy, optional two-way only for safe groups, loop prevention, managed membership provenance, preserve manual grants, remove only owned grants, reconcile offline changes. Block OP, admin, wildcard and inherited dangerous groups/roles; role hierarchy checks and fail closed when unsafe. No automatic privilege elevation from a newly acquired Minecraft permission. Reconcile managed benefits after punishment/expiry from current policy.

## 7. Trusted operations and staff authorization
After verified link, authorized Discord roles and independently approved identities qualify for per-server profiles. Bypasses alter OrionGuard policy only, never grant underlying Minecraft permissions. Separate categories: resolved sensitive command allowlist, WorldEdit/FAWE per-operation and cumulative budgets, mass block/entity operations, selected permission management, item/inventory and teleport operations, maintenance, exempt authorized work from automatic containment. Protected regions/worlds, hard safety ceilings, no self-approval or unrestricted wildcards. Temporary task-specific authorization (actor, server, region/world, operation, max budget, expires, approver), optional second approval. Role removal, unlink, suspension, lockdown or stale lease revokes exemptions; audit all operations, including trusted work, to staff-activity channel. No exemption from audit or active sanctions. Ordinary OP/wildcard never establishes trust. Use resolved command identities and API hooks, not text-only filters; document unsupported paths.

## 8. OrionGuard detection and containment
Detect unexpected OP, sensitive permission/group/inheritance mutation (LuckPerms), protected command attempts, unauthorized plugin management, WorldEdit/FAWE edit sessions, mass break/place, TNT/explosions, containers, entity spikes, join raids, suspicious relinking, ban-related correlation. Rule configuration: enabled, severity, thresholds/windows, exclusions, cooldown, alert route, containment type/duration, approval. Aggregate and update one persistent incident rather than per-block spam; severity notification roles configurable. Local enforcement before damaging supported operations, actual observed change counts and partial edits distinguished from requested volume; attribution actor vs affected target, unknown when no evidence. WorldEdit/FAWE dedicated integration, atomic concurrent edit budgets and protection coverage tests, no guarantee for unsupported direct writes. CoreProtect evidence on demand; no synchronous per-block queries. Default automatic response reversible containment for reliable policy violations, not speculative matches. Lockdown configurable server/guild, trusted access policy, console recovery. No permanent automatic ban based on an anomaly.

## 9. Configurable moderation and appeals
Types: warning, kick, Minecraft mute, Discord timeout (platform maximum 28d), freeze, build/WorldEdit/command restriction, quarantine, managed role suspension, temporary/permanent ban. Validate supported type/platform combinations, Discord hierarchy and permissions. Duration presets 5m,15m,30m,1h,6h,12h,1d,3d,7d,14d,30d, permanent; custom composite times, overflow and invalid inputs rejected. Scope server, selected guild Minecraft servers, Discord only, cross-platform. Reason, evidence, moderator identity, policy/template version, start/expiry UTC, case ID, approval. Staff duration caps, role hierarchy, separate permissions and independent approval for sensitive actions. Configurable presets and repeat-offense windows, e.g. spam mute 15m/1h/1d, confirmed grief 7d ban, unauthorized edit 1h quarantine; examples not hardcoded policy. Manual issue/review from incident card or player profile, edit/extend/shorten/revoke with reason, appeal via optional OrionTickets. Lifecycle created/pending approval/pending delivery/active/partial/failed/expired/revoked; ACK required per target. Offline player enforced on next join, offline server durable queued action, expired queued sanctions never resurrected. Absolute expiration, restart reconciliation, independent overlapping restrictions, preserve third-party sanctions. Player notification with case/reason/duration/appeal; ban disconnect message. Cross-platform failures visible, no false success. Automatic expiration, bounded scheduler, no per-player timer tasks.

## 10. Account correlation
Only authenticated Minecraft client addresses from trusted forwarding; Discord bots cannot see Discord IPs. Guild-keyed HMAC-SHA256 normalized IP fingerprint, no raw IP sent or logged, IPv4-mapped IPv6 normalization, separate key version per guild, retention 90d example; protected keys and rotation semantics. Correlate linked Minecraft/Discord identities across registered servers within guild; indexed lookups, manual compare two accounts and automatic match alerts. Shared household/VPN/CGNAT false positives, documented exceptions, staff review, never auto-ban from IP match alone. Unknown/proxy-only address means no reliable match. Audit searches; no public IP data, no external IP lookup. Pseudonymous data still sensitive; disclose purpose and retention, deletion policy.

## 11. Evidence and incident center
Persistent private Discord alerts: server, severity, player and linked Discord at event time, actor/target separated, source, world/region, action, allowed limit, requested/observed count, blocked/partial/succeeded/unknown, timestamp, incident ID, related events. Buttons View Evidence, Profile, Investigate, Punish, Quarantine, Acknowledge/Dismiss; fresh staff checks. Evidence tabs timeline, identity, permissions, WorldEdit/FAWE, CoreProtect, notes, correlation. Structured source IDs and confidence (observed/inferred/reported/unavailable). Preserve immutable historical snapshots independent of later unlink. Checksums, append-only/tamper-evident records and off-server replication, no guarantee against privileged host tampering. Bounded sanitized evidence export JSON/CSV/report/ZIP, permission-gated, audit downloads; staff attachments restricted. Configurable 90d events/365d incidents, legal hold/expiry policies. Rollback preview with actor/world/time/count and scope, explicit approval and integration capability check; cannot recover unlogged changes. No remote arbitrary commands or direct DB edits. Alert delivery deduplication and persistent message ID; deleted Discord message does not delete evidence.

## 12. Configuration and docs
Versioned config.yml, verification.yml, security.yml, roles.yml, punishments.yml, staff.yml, chat.yml, messages.yml, menus/java-inventory.yml, java-dialogs.yml, bedrock-forms.yml. Main config retains mode, bind, port, endpoint, token, interval, privacy and skins. Merge missing defaults only, preserve unknown/false/empty/custom values, strict parse, backup before atomic validated replacement, no rewrite for future/malformed configs, migration failure visible and fail closed for security. Local hard safety limits take precedence over remote config. Humanized README, setup guide for Pterodactyl Pull, protocol/security docs, moderation and evidence guides, config reference, changelog and known limitations. Version bumps consistent with build descriptor; do not advertise unimplemented controls.

## 13. Implementation stages and checks
A. Import baseline, adapt standalone build, preserve v1 behavior and smoke checks. B. Typed v2 protocol, auth/replay/isolation, durable stores and migration. C. Identity and gate, Java/Bedrock/auth integrations and verification dashboards. D. Moderation engine, approval and expiry, Discord actions/ACKs. E. Role sync, chat, channel manager and trusted operations. F. OrionGuard integration, incident/evidence/correlation and rollback review. G. Full dashboards, performance, docs and release. OrionBot integration is required separately; staging a plugin alone cannot deliver Discord-side features.

Regression checks: v1 compatibility; Java25 Maven and Node tests; malformed configs and no token overwrite; simultaneous links and replay; spoofed offline UUID/Bedrock, auth bypass and reconnect; role and command privilege escalation, stale lease and lockdown; cross-guild isolation; punishment overlap, invalid duration, crash/retry/expiry, platform failure; chat loops and mention injection; trusted builder and denied edits, FAWE concurrent budget, unknown actor; network correlation false positives and retention; evidence export ACL and durable delivery; load testing queue bounds and tick timings; live Java and Bedrock UI tests; real Discord/Pull reverse proxy smoke. No stable release until acceptance, explicitly mark untested integration paths.
